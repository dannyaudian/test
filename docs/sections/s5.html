5

Concept & Details

Four concept layers: design principle, straight-through data flow, standard data handling logic, and customer journey per stage.

Layer 1

FAST Decign Principle

Frontman-drivenInput-onceSystem-controlledSeamless front-to-backCompliance-secured
  • The Frontman enters customer and transaction data at the initial source.
  • Administration verifies and completes internal data.
  • The system prevents redundant input.
  • Valid data is reused.
  • The SPK, SO, billing, payment reference, and receipt numbers are connected.
  • Every verified payment produces an e-receipt.
  • Data is carried from SPK through to STNK/BPKB.
  • A waivable failed compliance rule is routed to the decision owner.
  • Every change has an audit trail.
Core statement

The Frontman captures customer and transaction data once. Administration verifies and enriches only where required. The system carries the same validated data and document references from SPK through Sales Order, billing, payment, receipt, AFI/DO, delivery, Good Issue, and document completion without re-entry.

Layer 2

Straight-Through Data Flow

Frontman InputCustomer, transaction, unit request, documents, payment request, delivery preference, and compliance exception request when eligible.
System ValidationFormat, completeness, duplicate checking, master-data matching, document validity, payment verification, and reference integrity.
Administration Verification and EnrichmentVerification and the addition of internal data that is genuinely new.
Single Source of TruthCustomer, transaction value, vehicle, payment, receipt, document, compliance, and exception-decision data.
Automatic Data Carry-ForwardSPK No. → SO No. → Billing No. → AFI/DO → Delivery → Good Issue → STNK/BPKB. Every verified payment reference produces one receipt number within the same transaction lineage.
Open Kitchen VisibilityThe Frontman, Administration, Finance, management, and customer see the status from the same transaction.

Layer 3

Standard Data Handling Logic

Step 1 — Capture at source

Data is entered by the party with the most valid source information.

Step 2 — Validate

The system checks format, completeness, duplication, master data, and reference integrity.

Step 3 — Verify or enrich

Administration verifies the data and only adds internal data that is not yet available.

Step 4 — Store as source of truth

Valid data is stored as the official transaction data.

Step 5 — Reuse downstream

The data is used automatically by the next process without re-entry.

Step 6 — Correct at source

If there is an error, the correction is made on the original data and not through a different input at a later process.

Step 7 — Control changes

Changes after a transaction lock or compliance exception decision must use a workflow, version control, and audit trail.

Layer 4

End-to-End Customer Journey

SPK No.→Booking Fee/DP + Receipt→SO No.→Settlement + Receipt(s)→Billing No.→AFI/DO→Delivery→Good Issue→STNK/BPKB

Each stage has: Frontman action, Administration action, system-generated data, data carried from the previous stage, new data genuinely required, system validation, compliance gate, and output used by the next stage.

Stage 1

SPK

Frontman inputs

  • Customer identity.
  • Customer contact.
  • Buyer address.
  • STNK name and address, including district/city.
  • Purchase method (cash or leasing).
  • Unit type and colour.
  • Accessories.
  • Customer documents for SPK entry.
  • Documents for later STNK/BPKB filing.

Administration role

  • Verify customer data.
  • Verify documents.
  • Identify missing or invalid requirements.
  • Add internal classification if required.

System generates

  • Customer ID.
  • SPK number.
  • Area PO from kabupaten/kota on the STNK address.
  • OTR price from that PO area.
  • Repeat-order status.
  • Document readiness.
  • Minimum booking fee according to the selected unit.

Data carried forward

Customer, transaction, unit, document, and compliance data are used by the booking fee/DP request, Sales Order, billing, AFI/DO, delivery, and STNK/BPKB.

Business rule

Customer and transaction data captured at SPK must not be re-entered at subsequent stages. Unit OTR follows the PO area generated from kabupaten/kota on the STNK address. Booking fee is billed only after this SPK data is saved.

Stage 2

Booking Fee/DP and Sales Order

Frontman action

  • Save the SPK.
  • Monitor the booking fee invoice the system sends to the customer.
  • Confirm the payment instruction if it needs to be resent.
  • Submit the Sales Order request after the unit's minimum booking fee is verified.

Administration role

  • Handle unmatched or exceptional payment only.
  • Does not re-enter payment status.
  • Does not set the booking fee amount manually.

System process

  • Pull the minimum booking fee from the unit master.
  • Send the booking fee request to the customer as soon as the SPK is saved.
  • Generate payment reference.
  • Verify payment.
  • Match payment.
  • Generate a unique receipt.
  • Link receipt to SPK.
  • Compare incoming amount with the unit minimum.
  • Convert the saved SPK into a Sales Order only when the booking fee meets the unit minimum.
  • Carry buyer, STNK, unit, PO-area price, accessories, and documents without re-entry.
  • Generate SO number with originating SPK reference.
  • Add SO reference automatically to receipt lineage.

Customer sees

  • Booking fee request locked to the unit master (not self-entered amount).
  • Digiroom link: pay.fast.id checkout with locked QRIS/VA.
  • Frontman QRIS: scan the barcode on the salesperson screen; the phone only confirms the same amount.
  • EDC is not shown on the customer phone.

Data carried forward

  • Customer ID.
  • SPK number.
  • Sales Order number.
  • Unit data.
  • Transaction structure.
  • Booking fee/DP amount.
  • Payment reference.
  • Receipt number.
  • Payment verification.
Business rule

After the SPK is saved, the system bills the booking fee to the customer. The minimum amount follows the selected unit. Without a booking fee verified against the unit minimum, there is no Sales Order. When the booking fee is met, the SPK data is converted into a Sales Order — not re-entered. The receipt is linked to the SPK, then the SO number is added to the lineage.

Stage 3

Settlement Payment and E-Receipt

Frontman action

  • View AR Open per unit or Sales Order.
  • View active payment requests.
  • Create settlement payment request within Available Request Amount.
  • Resend, adjust, or cancel an active request.
  • Monitor partial or full payment.
  • View accumulated active receipts.
  • View outstanding balance.

Administration role

  • Resolve unmatched payment.
  • Handle documented exception.
  • Does not recalculate outstanding manually.

System process

  • Calculate AR Open from active receipts.
  • Calculate Available Request Amount after deducting active payment requests.
  • Validate request nominal against real-time availability.
  • Expose open unit bills on Customer Home.
  • Record every verified payment.
  • Allocate payment.
  • Generate one unique receipt for each verified payment.
  • Reduce AR by the active receipt amount.
  • Link every receipt to the payment reference, SPK, SO, and billing document when available.
  • Deliver the digital receipt to the customer.
  • Close or adjust overlapping payment requests.
  • On receipt cancellation, restore AR and reclassify the linked request.
  • Calculate accumulated active receipts.
  • Determine Partially Paid or Fully Paid status.

Data carried forward

  • Payment and receipt history.
  • Billing readiness.
  • Account Receivable monitoring.
  • Delivery eligibility.
  • Management dashboard.
  • Customer notification.
Business rule

Every verified payment is recorded once, assigned one unique receipt number, and deducts AR by the active receipt amount. Pending requests do not reduce AR. If a receipt is cancelled, AR is restored, the linked request is reclassified, and all dependent financial gates are recalculated.

Stage 4

Billing

Frontman action

  • Submit billing-readiness request.
  • View every failed compliance rule.
  • Complete missing requirements.
  • Submit compliance exception only when the failed rule is marked waivable.

Administration and Finance role

  • Verify compliance evidence.
  • Confirm whether the failed requirement has been completed.
  • Review eligible compliance exception without changing transaction data.
  • Does not re-enter customer, unit, payment, or Sales Order data.

System pulls automatically

  • Customer data.
  • SPK number.
  • Sales Order number.
  • Unit information.
  • Final transaction value from source system.
  • Purchase method.
  • Booking fee according to unit.
  • Payment and receipt history.
  • Funds-in percentage.
  • Full DP required and received from B2B leasing (shown on the Sales Order pricing structure when payment type is credit/leasing).
  • Leasing e-PO (customer total DP, financed amount, tenor) from B2B.
  • Settlement status.
  • Outstanding balance.
  • Document readiness.
  • Compliance-gate results.
  • Active exception decision, conditions, and expiry.

System generates

  • Billing readiness.
  • Billing Locked or Billing Ready status.
  • Failed-rule and lock reason.
  • Exception eligibility and decision route when waivable.
  • Billing document number after the gate is passed or a valid exception permits conditional release.
  • Permanent linkage between billing number, Sales Order number, and originating SPK number.
  • Automatic enrichment of related receipt lineage with the billing number.
Business rule

Billing uses validated upstream data and must not require transaction re-entry. For cash, billing only unlocks once at least 30% of the transaction value has been received. For leasing, billing only unlocks once the full DP has been received and the leasing e-PO exists (total DP, financed amount, tenor); both are pulled from B2B. Without an e-PO, paperless billing only goes through the Operation Manager. SPK and SO references must stay consistent. The 30% cash / full leasing DP requirement is non-waivable.

Stage 5

AFI/DO

Administration inputs

Only new administrative data that is not yet available from the previous process.

System pulls automatically

  • Customer identity.
  • STNK name.
  • Customer address.
  • Supporting documents.
  • Sales Order.
  • Unit type.
  • Color.
  • VIN.
  • OPO/OPK.
  • Billing status.

System process

  • Auto-populate AFI.
  • Auto-populate DO.
  • Match customer and vehicle data.
  • Identify mismatch.
  • Lock only affected SO.
Business rule

No manual re-entry of validated customer, STNK, Sales Order, or vehicle data.

Stage 6

Delivery

Frontman inputs

  • Delivery request.
  • Delivery schedule.
  • Delivery location.
  • Recipient information.
  • Customer confirmation.

Administration role

  • Verify operational readiness.
  • Handle delivery exception.
  • Does not re-enter financial status.

System pulls automatically

  • Customer data.
  • Unit and VIN.
  • Billing status.
  • AFI/DO status.
  • Purchase method.
  • Payment history.
  • Outstanding balance / paid in full status for cash.
  • Leasing contract signed status from B2B leasing.
  • AR status.
  • PDI status.
  • Delivery authorization.

System generates

  • Eligible for Delivery.
  • Locked for Delivery.
  • Hold reason.
  • Required action.
Business rule

Delivery eligibility uses the same upstream data. For cash, delivery only unlocks after the transaction is paid in full. For leasing, delivery only unlocks after the contract has been signed by the customer; the signed status is pulled from B2B leasing. This delivery requirement is non-waivable.

Stage 7

Good Issue

Frontman inputs

  • BSTKB.
  • Customer signature.
  • Vehicle receipt photo.
  • VIN / identity photo.
  • Timestamp and geotag.
  • Power of Attorney when applicable.

System pulls automatically

  • Customer.
  • Sales Order.
  • Unit.
  • VIN.
  • Recipient from SPK.
  • Delivery authorization.
  • Financial clearance.
  • AFI/DO.
  • PDI status.

System process

  • Validate evidence completeness.
  • Match delivery with SO and VIN.
  • Record Good Issue.
  • Publish the same evidence pack to the customer account.
  • Close delivery milestone.
Business rule

Good Issue must use existing customer, unit, and delivery data without re-entry. The evidence pack is the authentic record — not dealer CCTV. Cash still cannot be handed over before paid in full.

Stage 8

STNK/BPKB

Administration inputs

Only new information related to the vehicle document process and its completion.

System pulls automatically

  • Customer identity.
  • STNK name.
  • Customer address.
  • Unit.
  • VIN.
  • Sales Order.
  • AFI/DO.
  • Delivery date.
  • Supporting documents.

System process

  • Track milestones.
  • Detect aging.
  • Send escalation.
  • Notify Frontman and customer.
  • Close completed document milestones.
Business rule

Customer and vehicle data validated at the front must continue through document completion without being typed again.
