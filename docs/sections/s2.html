Cross-functional foundation — who fills in what, where the data goes

Before redesigning the system and workflow, a thorough review and mapping of all data used in the process will be carried out.

Objective

To clearly determine:

  • Data entered by the Frontman.
  • Data verified by Administration.
  • Internal data added by Administration.
  • Data generated automatically by the system.
  • Data and decisions under the Compliance Exception Approver's authority.
  • The System of Record for each data element.
  • The downstream processes that use that data.
  • Data that is currently still entered repeatedly.
  • Data that can be carried directly from front to back.
  • The relationship between the SPK, Sales Order, billing, payment reference, and receipt numbers.
  • Data displayed on the Customer Home.

Data ownership principle

Frontman inputs

The Frontman enters data obtained directly from the customer and initial transaction information, including:

  • Customer identity.
  • Customer contact.
  • Purchase method.
  • Transaction structure.
  • Unit request.
  • STNK name.
  • Customer documents.
  • Payment request.
  • Delivery preference.
  • Compliance exception request when eligible.

Administration verifies and enriches

Administration does not re-enter the Frontman's data. Administration is responsible for:

  • Verifying data and documents.
  • Ensuring compliance with requirements.
  • Adding internal data not yet available.
  • Determining document readiness.
  • Handling unmatched payments.
  • Ensuring vehicle and document matching.
  • Processing administrative status.
  • Verifying compliance exception evidence.

System generates and calculates

  • Customer ID.
  • SPK number.
  • Sales Order number.
  • Billing document number.
  • SPK–SO–Billing document linkage.
  • Payment reference.
  • Virtual Account.
  • Payment status.
  • Payment allocation.
  • One receipt number for every verified payment.
  • E-receipt PDF.
  • Accumulated payment.
  • AR Open.
  • Available Request Amount.
  • Billing readiness.
  • Delivery eligibility.
  • Timestamp.
  • Audit trail.

Compliance Exception Approver decides

The Approver only decides exceptions that come from a failed compliance gate and are declared waivable by policy:

  • Approve with conditions.
  • Reject.
  • Return for completion.
  • Decision reason.
  • Required condition.
  • Validity period.
  • Scope of temporary release.

The Approver does not re-enter transaction data, does not change transaction values, and cannot override rules that are non-waivable.

Core Data and Financial Rules

  1. One field, one owner, one source of truth.
  2. Data is entered at the first most valid source.
  3. Administration verifies and completes, rather than re-copying.
  4. Valid data is carried to all downstream processes.
  5. Derived data is calculated by the system.
  6. Corrections are made at the original data source.
  7. Valid changes are propagated to the next process.
  8. Re-entry is only allowed as a documented exception.
  9. Every change has an actor, timestamp, reason, and audit trail.
  10. Every Sales Order stores the originating SPK number.
  11. Every billing document stores the Sales Order number and the originating SPK number.
  12. Every verified payment produces one unique receipt number.
  13. A payment request that is not yet paid does not produce a receipt.
  14. The receipt is connected to the payment reference and the available transaction documents.
  15. If SO or billing has not been created yet, its reference is added automatically once the document is issued without changing the receipt number.
  16. Every active receipt is available as an e-receipt PDF customers can view and download.
  17. The e-receipt contains the receipt number, status, customer, unit, amount, date, payment method, payment reference, SPK, SO, billing when available, and the verification code.
  18. AR Open = the unit invoice value minus total active receipts.
  19. A payment request that has not yet produced a receipt does not reduce AR Open.
  20. Available Request Amount = AR Open minus the total active payment requests that are not yet paid and not yet expired.
  21. Frontman can only create payment requests up to the Available Request Amount.
  22. Customers can open all unit invoices that are still open from the home.
  23. Payment directly from the Customer Home uses the same AR Open.
  24. Overlapping payment requests are closed or adjusted automatically to prevent overpayment.
  25. Receipts must not be overwritten or deleted without history.
  26. Corrections use reversal or reissue with a reference and audit trail.
  27. A cancelled e-receipt remains visible as history with a Cancelled status.
  28. A cancelled receipt is not counted as active payment proof.
  29. Cancelling a receipt returns the amount to AR Open.
  30. The related payment request changes to Cancelled or Requires Follow-up.
  31. Billing and delivery gates are re-evaluated after a receipt cancellation.
